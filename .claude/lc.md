# lc — issue and release lifecycle (reference for `.claude/lc.js`, Workflow V5.2)

Production since the cutover 2026-11-11 (lifecycle-data db1ea74d7): planning/roadmap.md and problems.md are rendered by lc.

The policy digest is workflow.js + evidence.md + routes.md; lc.js is outside it, so an lc fix does not void open tasks; `.claude/lc.test.js` guards it (`node --test .claude/lc.test.js`, ~70 s, needs git). Rules it enforces are stated in planning.md and git.md.

CLI: `lc.js` (node only) and `lc.test.js` (behaviour tests on scratch repos with a bare fork and origin). Data: the ref `ivan/lifecycle-data`, an orphan branch
that is never checked out.

## Context, not files

Why (measured over 622 transcripts of 11-10..11-11): planning and policy reads cost about 2.66 M tokens, and the cost is the number of reads and re-reads, full reads of target-architecture docs and explicit re-reads of CLAUDE.md, not the size of problems.md (grepped, about 2.3 k characters per read).

- **Paged packs.** `lc show <step|release> [--page N] [--role rc]` is an agent's pack: the row, its issue lines (with `why` notes), direct dependencies (open lines, or archived with their closure) and the decisions that apply. The budget is `meta.budgets` (pack 12 KB, rc 2 KB). Over it, the pack is paged with a header (`page 1/3 · lines 1-30 of 74 · next: …`); a line is never cut or dropped.
- **Growth diagnosis.** `lc status` prints a `growth:` line, and `lc check` lists the causes: `dup?` (two open issues share an exact quoted member `Module.method` and a rule number; a module name alone, or a name shared by more than 6 issues, is not evidence), `broad` (a row over `rowIssues` 25), `stale` (check.js "member gone" on problems.md lines), triage, tails due, and resolved issues waiting for close. Each cause has an owner action; nothing is merged or deleted.
- **Warnings on intake.** `add` and `edit --sites` print open issues that quote the same code name. `start` prints open issues naming a module from the V5.2 brief's `cause.chain`.
- **Kinds and validation.** `add --kind <bug|risk|missing|debt|gap>` (required; a bug or a risk refuses a `--what` without `→ what is seen`), `kind <kind> <id...>` sets many in one write, `kind` alone prints the counts and the unclassified ids per section. `list [--kind k|none] [--sec s] [--at step|triage|tail] [--unseen]` prints issue lines; `near <id|step|Module>...` prints the open issues on the same modules for whoever reads that code (a module named by more than 12 issues is listed only when asked for by name; an id or step that matches nothing is refused); `seen <id...> --by <who date>` stamps a confirmation; `drop --gone <file:line>` closes what the code no longer has (as `--rule0`, not in a landed step or a frozen release). A kind changes no view line.
- **Assembling a release.** `next` (read-only) prints the fix queue (open bugs, then risks, that no landed step holds), each live release with its age and landed steps (a fix release open for 24 h is at its limit; it has no limit of steps), the next planned release step by step (issues, without a kind, not confirmed, debt or gap as a count) and the list of what must happen before it opens. `open` refuses while a bug or a risk has no release; `start` refuses a step over 4 issues unless `step set <step> --plan <file under planning/>` names its plan (a planned release's step, or a class step of a fix release: one rule broken at several sites; any other fix step is split). A debt or gap in the tail comes due two releases after its last `seen`, not its origin. `status` prints the fix queue when it is not empty.
- **A frozen release that needs a fix.** `unfreeze <release> --decision <id> --reason <what the final runs showed>` (the decision allows `action=unfreeze,release=<key>`) opens it again; the old head, its freeze time and any gates recorded on it move to the release's `thawed` history and the gates start empty. The fix goes in as a new step by the usual path; `freeze` then takes the new tip and every gate is recorded on it.
- **Size only warns.** `render --write` notes a view over an old KB budget instead of refusing. `render --check` (used by hygiene) fails only after the cutover, when a view is not the render.
- **Measurement.** `.claude/tools/token-usage.py --from <release open> --table --only <the release coordinator's session ids, comma>` prices the release's sessions and agent launches from the transcripts and counts batched tool turns (without `--only` the total also holds the flow and economy sessions; the ids are the first 8 characters the table prints after `session`); `flow-stats.js --since <release open>` counts records, restarts and lifecycle writes; `context-cost.py [--since --until]` counts planning and policy reads. The RC runs them at release close, and `gate <rel> report` refuses a report without the `total $…` line of the first and the `task records …` line of the second. The report also carries the `per detector: …` line of `node planning/rules-check.js --all --root <the release tree>`; the gate keeps the counts and refuses a detector that grew since the last closed release, unless the report says `accepted growth: <detector> <why> <decision id>`. Two more lines are required: the last line of `node planning/architecture/check.js --root <the release tree>` (`map references gone: 0 (code at <frozen head>)`: a name the map quotes and the code no longer has refuses the gate), and, when the release landed a task, `sample audit: <n> claimed · recorded <lc ids|none> · refuted <n>` with `--audit <file>`: `lc sample <release>` names three landed tasks picked by the frozen head, one auditor that has not seen the reviews answers the hard rules for their commits (brief: workflow/audit.md), the coordinator checks each claim and records what holds; the gate compares the line with the file and the ids with lc.
- **Intake.** `add` needs `--kind`. A `debt` or `gap` also needs `--task <slug>` (a task record whose brief scope names the module in `--sites`) or `--pass <audit|final-run|design|sweep>`: beside a task only a bug, a risk or a missing behaviour is recorded.

## Architecture (accepted 11-11)

- **One place per issue.** `issue.at` is a step key, or null for triage/tail. Releases list steps, never issue ids.
- **One commit per write.** Each write is checked against the fork's copy (`ls-remote`), moved by compare-and-swap (`update-ref new old`), and pushed without force. A refused push undoes the local move.
- **Sync without force.** `lc sync` fast-forwards or pushes. On a divergence it keeps this copy's commits at `refs/lc/conflict/<time>`, takes the fork's data, and prints the commands to run again.
- **Views.** `roadmap.md` and `problems.md` render in their V5.1 formats. `render --write` writes temp files first, then commits the data, then renames the files. A failure leaves either the old state or one that a rerun finishes. It refuses a hand-edited view (the change is redone through `lc add`, `edit` or `drop`; then `--overwrite-problems` or `--overwrite-roadmap` replaces the file and keeps the hand copy) and a copy the fork has moved past. `lc edit <id>` changes an open issue's text, alias and note; nothing reads the views back.
- **What a task leaves and changes.** `land` reads the task record's review table and brief: each `left` line must name an open issue (it then shows `left standing by <slug>` in `lc show`) and a decision it cites must exist; the step keeps the `left` list and the brief's `map` entries. `gate <rel> report` refuses while a map file named by a landed task says `Checked at` a commit that does not hold that landing: refresh the entry first.
- **Evidence.** Task records and run directories are read; lc writes none itself, but `gate ci` runs `workflow.js ready`, which refreshes that record's ready receipt. lc pushes nothing to origin and opens no PR.

## Gates lc enforces (from the 11-11 audit) and their tests

| Item | How lc meets it | Test |
|---|---|---|
| P0 close | an issue in a landed step needs its own result (`lc resolve <id...>`: several ids in one command, all proven or none written): a regression test (old fails, new passes, on its landed head) of any task of the step that landed inside the step's head and whose brief names the id, or a run of a commit holding the landing whose verdict has "ID: resolved". `close` refuses the unresolved, or `--carry` moves them | close: … never archived |
| P0 ci | asks `workflow.js ready` (the one owner of CI completeness) on the frozen head and requires its `ci` part: full PR checks, rules-check, no missing selected or raw-geodata tests | end to end (incomplete CI, wrong head, old rules) |
| P0 trace/ab | run.json resolved to one full commit equal to the frozen head; directory names it; not dirty; exit 0; scenario, script and window fit the profile; artifacts present (trace adds world.sqlite); coverage, invariants and verdict files name the run and head; "verdict: pass" required; sha256 of each kept. A/B: both scenarios on both sides, A any other commit (the version players have), one save, diagnostics on | end to end (wrong SHA, dirty, short, missing artifact, misnamed, fake or failed verdict) |
| P0 no bypass | code gates cannot be waived (`--waive`/`--decision` refused); `lc gates` cannot drop ci, trace, ab or report; `drop --rule0` refuses an issue of a landed step or a frozen release | end to end |
| P0 validated ≠ published | `close` archives as `validated, published: null`. `lc publish` only records a publication someone made with the maintainer's authorization: a decision that allows `publish` for that release, plus origin's branch containing the head | end to end |
| P1 render | temp → data → rename; refuses on a moved fork even when the data is unchanged | views |
| P1 remote | `ls-remote` is the tip; a failed or disagreeing fetch refuses; freeze takes the fork's tip and refuses when local differs | remote truth |
| P1 decisions | `decide --allow action=…,issue=…,to=…`; every `--decision` is checked against the action and subject (rule-override, scope-add, cap, order, land-no-code, drop, split, publish, gates, placement-rule) | decisions … |
| P1 place | only one naming row or one explicit `lc placement` rule (itself authorized); the section heuristic is gone | views |
| P1 writers | fork check before write, push after, `sync` with conflict refs | writers |
| P1 tools | `split` (old id, aliases and history stay; new id records `split from`), `tails` (due two releases on), `step set|move|drop`, `release drop` (an empty planned release), `dep` | split … |
| P1 rc-tools | `land` and `check-candidate` read B from `RC_BRANCH` or `lc get $RC_RELEASE branch`; no default | manual (.claude/tools) |
