# Planning and roadmap

## Problems, plans and the roadmap

- Review/audit findings: an agent lists each finding as a ready `lc add` line in its report and does not run `lc` itself; the coordinator runs those lines before the next launch (they enter triage); no findings file.
  - What a planner or reviewer records beside its task (maintainer 2026-11-12: issues arrive faster than they close; 84 of 179 in two days came from these two roles): a `bug` or `risk` with what is seen after `→`, or a `missing` with its C4 source. A `debt` or `gap` is recorded only on code the task itself changes (or taken in as a small fix); elsewhere it is left unrecorded: whoever next works on that code reads it again. Final runs, audits and design passes record what they find as before. `lc add` holds this: it needs `--kind`, and for a `debt` or `gap` `--task <slug>` (that task's brief scope names the module) or `--pass <name>`.
- One problem = one lc issue (its line in `architecture/problems.md`: id | origin | rule | file:line | what is
  wrong → impact | fix | tag), whatever found it; a problem already there gets the new finder's id as an alias. Other
  files cite the id, never copy the evidence. The tag comes from the issue's place in lc: `[rN]` (a row of release N),
  `[large]` (its own plan), `[tail]` (small, here only, or triage). At each release boundary a `[tail]` whose origin
  date (for a debt or gap: its last confirmation, `lc seen`) is two releases old moves to a roadmap row (`[rN]`), is deleted with its reason (rule 0: not worth its cost; `--gone`: the code no longer has it), or, a debt or gap that still holds, is confirmed again;
  `lc tails` lists the due ones (part of the growth diagnosis; maintainer 2026-11-10, sizes as guides 11-11).
- Kinds (maintainer 2026-11-12): what an issue is decides where it lives and how it ends. Set with `lc add --kind` or `lc kind <kind> <id...>`, read with `lc list --kind <kind>`; required at `lc add` (`lc kind` classifies the older issues).
  - `bug`: a player sees wrong behaviour. `risk`: the server can fall, hang or lose data. Both say what is seen after `→` in the what field, go to a fix release (or sit in the planned step whose mechanism is their fix) and close by their own result (`lc resolve`; a small fix: `lc drop --fixed-by`, below). A risk may instead be accepted by my decision. Their count does not grow from one release close to the next (`lc status`, the kinds line).
  - `missing`: C4 has it and we do not, or we differ on purpose. It names its C4 source and sits in a feature release.
  - `debt`: a rule broken with no symptom. `gap`: no counter, test or limit. Both stay with the code (`[tail]`), not parked in a release row: the task that touches their site takes them in, or one task closes a module's batch.
- Validating an issue is three answers with evidence: still true (file:line today), what a player or the server sees, not a duplicate.
  - At `lc add` the finder gives them.
  - At every touch the task's planner gives them for the open issues on the code it reads; the `l2-planner` type carries the instruction (`lc near <step|id|Module>`), the coordinator records the answers: still true → `lc seen <id...> --by <who date>`, gone → `lc drop <id> --reason … --gone <file:line>`, taken into the task → `lc assign`.
  - At a release close: the sections the release touched.
- Assembling a release (maintainer 2026-11-12). `lc next` prints the fix queue, the live releases, the next planned release and what it still lacks.
  - A fix release assembles itself: every `bug` or `risk` with a verified cause enters it (one without a cause enters as an investigation step and leaves if none is found); debt and gap on the same code ride along when the planner takes them in. An issue marked as a deeper cause goes first, before its symptoms and before every other bug; then bugs before risks, then by player impact. It freezes when it has been open 24 h; what has not landed waits for the next one. It has no limit of steps (maintainer 2026-11-13: the six-step limit is removed; one pair of final runs then judges a day of fixes, so a regression the runs show is searched among all of them). Its steps are split to one cause each and get no plan file, except a class step (below) that holds more than 4 issues: it gets one (`lc step set <step> --plan <file>`: the owner's fix first, then the sites; maintainer 2026-11-13); a batch of small fixes (below) is one step (each fix is its own commit, so a bisect names it and a revert removes it). Issues of one class (one rule broken at several sites: timers outliving their body, a failed goal picked again) are one step fixed in the mechanism that owns the rule, not a step per site; the readiness pass names the classes.
  - A planned release is its roadmap row in my order. Before it opens, a readiness pass by a cheap agent confirms each issue against the code (`lc seen`, `lc drop --gone`), splits the row into steps of at most 4 issues or names the step's plan with its order of commits (`lc step set <step> --plan <file>`: the step's file under target-architecture/), and sends debt and gap the mechanism does not own to the tail. Then I get one message with the result (steps, issues, gone, moved) and answer once for the whole release.
  - Deeper causes (maintainer 2026-11-12: fix the cause, not the symptom; the deeper cause always matters more; 3 of 11 landed tasks of 1b fixed the nearest cause and left the one under it). A task fixes the deepest cause it can prove, in its owner. It stops at a nearer one only when the deeper one is replaced by a planned release or needs its own critical task (evidence.md "Cause gate" says the same), and then says so: whoever writes the cause chain states it (the brief's `cause.deeper`; with a planner, its report carries the line), `deeper cause: fixed here` or `deeper cause: left as <id> because <reason>`. The coordinator writes it on the issue left: `lc edit <deep id> --origin "<its origin>; deeper cause of <symptom ids>"`, adding ids as more symptoms name it. The readiness pass reads these marks to order the release.
  - Triage is empty when any release opens: each issue has a kind and a place or is dropped. If bugs and risks grew over a release, the next one is a fix release.
  - lc refuses `open` while a bug or risk has no release, and `start` on a step over 4 issues without a plan; the rest of this bullet is the coordinator's to keep.
  - My decision is needed only for gameplay forks, which `missing` things to build, accepting a risk unfixed, and moves between numbered releases.
- Small fixes (maintainer 2026-11-12: bugs arrive faster than the full flow can pay for; some are fixed in passing). A small fix has no planner and no run of its own, and a test of its own only when a wrong fix would be silent: the review of the task that carries it, that task's CI and the release's final runs check it.
  - Small is all four: the issue names the cause as file:line and the fix in a sentence (seen by reading, nothing to investigate); the change stays in one module and adds no state, timer, path or config key; it changes no stored data, client protocol or per-tick path, and no file on a critical surface (`workflow.js` refuses a lower route for `database/`, `data/Bots/`, `src/Database.js`, `Situations.js`, any worker file, migrations, `TableFingerprint`, `scripts/generate`, `scripts/perf`: such a fix rides in a critical task or is its own); a wrong fix would show (a counted failure, a trace line, the release runs), or the fix carries one test that fails on the old code. A rule shared by hot and cold: only a fix inside the one function both call, and only as a ride-along in a task already on the critical route for that function (routes.md puts a shared rule on that route; a batch never takes one). Unsure → an ordinary task. (Conditions widened by the maintainer 2026-11-12: of 201 open bugs and risks 9 passed the first wording; the test clause passes about 23, the shared-function clause about 9 more.)
  - A small fix has no planner, so its implementer answers the deeper-cause line for it (`deeper cause: fixed in its owner` or `left as …`, as above); a fix that would need the owner changed for several callers is not small and goes back as an ordinary task (`left as` is not a way to land a patch at one call site) (2026-11-12: DT-300 fixed one caller of the worker's `send()` and left the others).
  - Carried one of two ways, each fix in its own commit with the id in its subject, named in the brief's `smallFixes` (id and the one source file; `ready` checks the commit against it). Ride-along: a task already changing that file or function takes at most 3. Batch: one task (`start --risk fast --kind chore`) takes one step of at most 4 from one area; the issues' own lines are the plan, implementer sonnet medium, one review opus high.
  - The review answers every hard rule for the whole diff as always; for a small fix whose wrong fix would show, rule 11 may be `N/A: small fix` (a test is still added where it is a few lines in an existing test file); one whose wrong fix would be silent carries its one test, and the review checks that it fails on the old code. A small fix the reviewer objects to is taken out (its commit dropped, the issue stays as an ordinary one), not argued in a fix round.
  - Closed after the task lands with `lc drop <id> --reason … --fixed-by <slug>`. When a final run fails and the bisect names a small fix, its commit is reverted and the issue returns as an ordinary bug: no second attempt in passing.
  - Who names them: whoever has the code open. A planner or reviewer names them in the module its task reads; the readiness pass names one only after two checks on the code, not on the issue's text: the file is on no critical surface (above), and the function to change has one calling module and one side (grep its callers: several callers, or main and worker both, is a shared rule and not small). Marked from text, 4 of the first 5 batch items did not hold (2026-11-12: two on a critical surface, one a shared rule with several callers, one not a defect). The coordinator carries them. At each release close the flow session counts small fixes landed, taken out by a review, reverted, and final-run failures traced to one.
- Planning state is lc (cutover 2026-11-11): the fork ref `ivan/lifecycle-data`, kept by `node .claude/lc.js`
  (reference `.claude/lc.md`), is the only source of issues, releases, placement, dependencies and closing. roadmap.md
  and problems.md are rendered views: never edit them. Create, edit, place, move and close only through lc (`add`, `edit`, `kind`, `seen`,
  `assign`, `place`, `dep`, `defer`, `land`, `resolve`, `close`, `drop`), then `lc render --write`. A hand edit of a view is
  refused, never taken in: redo it through lc. New issues enter triage; `place` uses only unambiguous rules (a row naming
  the issue, or a maintainer placement rule). An unknown root cause is an investigation, not leave to implement.
  Lifecycle data changes only by lc commands: no script calls lc's `save`; a correction no command covers waits for one.
- One queue: `roadmap.md` (rendered), numbered releases; a row is a lc step: a label plus ids or a plan file. Done means
  archived by lc (land, resolve and close; or drop with its reason and authority) and gone from the views.
- A roadmap step's plan lives in `target-architecture/step.md` and is deleted when the step lands; its binding
  decisions move first into the map, one clause on the row of the rule each shapes. Maintainer decisions taken outside
  a step go on the lc issue or the plan.md principle they shape.
- The map holds the current state only: an area line is rewritten to the new state, a paid problem is closed through lc (its line leaves the view);
  no history, no "was/now", no step or decision ids.
- One writer: only one agent at a time edits planning/ (the only editing agent, or the main session). Agents running in
  parallel put their planning edits (new issues for `lc add`, map clauses, limits rows) in their report; the main session applies
  them. Sizes are guides, never gates: hygiene prints a size note, nobody trims text to fit; growth is diagnosed (who
  reads it, how often: context-cost) and fixed at its cause. roadmap.md and problems.md have no size guide: lc keeps all open data; the
  context is budgeted (lc show pages a step's pack; growth is diagnosed by lc status/check with an owner action per
  cause: place, assign or drop with reason, decide a duplicate, refresh a stale line, split a broad row into steps); nothing is
  deleted or merged to save context.
- No unbounded growth: `node planning/hygiene.js` at every task boundary (exit 1 = clean up first). It fails on a file
  outside the list, on lifecycle views that are not the lc render after the cutover, on stale worktrees, stray files and perf runs
  beyond the kept sets, and prints size notes (planning files, CLAUDE.md 14 KB, 32 KB of policy per role) without failing;
  `--remove` removes clean merged or stale worktrees (branches stay). A new planning file only
  with my ok (added to the list in git.md "Where things are" and to `ALLOWED`).
- Planning files are for agents, not for me: I read reports in chat, never these files. Dense: one item per line, no
  hard wraps or blank lines, no headings or prose for a human reader, file:line instead of description; content stays
  exact (ids, file:line, numbers, reasons), code names in backticks (`check.js` finds stale names by them).
- One file per future release's design (`economy.md` for release 2), options as sections.
