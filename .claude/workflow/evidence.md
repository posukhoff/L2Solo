# Task evidence

## Cause gate and handoff

Separate symptom from hypothesis in the issue (`lc add`; problems.md is its rendered line): cause: guess or verified + trace/test/source ref. Guesses enter investigation, not implementation; critical blockers get immediate triage. A cause is verified when its chain runs from the observed symptom to the first wrong decision or broken invariant (C4 rule, situation, owner contract). The chain names where the symptom shows apart from the mechanism that produced it, rules out each plausible alternative with a handle, and is proven by a reproduction, trace or counterexample that accounts for the counted symptom, not one instance. Follow the chain to the deepest cause you can prove and fix that one, in its owner (planning.md "Deeper causes"); stop at a nearer cause only when the deeper one is replaced by a planned release or needs its own critical task, and then name it: `deeper cause: left as <lc id> because <reason>`. Before fixing the owning mechanism ask hard rule 0 of it: is it needed at all (deleting it is a fix). Unproven after one bounded investigation → blocker. Independent causes get separate linked slugs. Containment of a serious defect is labelled temporary, with an open root-cause lc issue. Briefs carry exact base and evidence handles; implementer spot-checks a decisive handle, reinvestigates only if contradicted. Coordinator resolves overlapping owner scopes before edits; review stays scoped.

Start with --kind fix (default), feature or chore. A guess is investigation-only. CLI validates shape, not truth; coordinator inspects evidence. New brief resets task evidence; changed policy requires new slug. Keep evidence handles, not secrets/log dumps. Sample:

```json
{
  "base": "<full task base SHA>",
  "symptom": "Observed incorrect town departure",
  "owner": "BotSpotTravel: departure/recovery",
  "cause": {"status":"verified","explanation":"What caused the observed failure","chain":["where the symptom shows (file:line)","first wrong decision or broken invariant (handle)"],"excluded":["plausible alternative ruled out (handle), or none plausible: reason"],"evidence":["run ID / trace record / source file:line"]},
  "scope":["src/..."],
  "nonGoals":["Unrelated field recovery"],
  "acceptance":[{"expect":"Expected observable behaviour","by":"test_bot_town_travel.js"}],
  "map":["world.md: Town departure"],
  "smallFixes":[{"id":"DT-375","file":"src/..."}],
  "evidence":["Saved run ID and SQL result reference"],
  "tests":["test_bot_town_travel.js"],
  "regressions":["test_bot_town_travel.js"]
}
```

Each acceptance line names what pins it in `by`: a test listed in `tests` (a case name may follow the file), or `run: <record>` / `trace: <record>` when only a run shows it. `map` names the architecture-map entries the task changes, each `<file>.md: <entry>`, or is one `none: <reason>`; the release report gate checks that each named file was refreshed after the landing. `smallFixes` (optional, at most 4) names each small fix the task carries (planning.md "Small fixes") by lc id and the one source file it changes: `ready` requires one commit per id, the id in its subject, changing that file and tests only.

A record ends by landing or by `close <slug> --evidence <ref>` with `--refuted` (a guess that proved wrong) or `--abandoned` (any task not landed: where its work went or why it stopped); a closed record takes no more evidence, and one opened under an older digest can still be closed.

A guess brief needs only base, symptom, evidence and cause hypothesis; complete owner/scope/acceptance/map/tests before verification. Feature/chore omit cause/regressions but supply goal, owner, scope, evidence (spec/reference), acceptance and tests. No source edits are done by CLI.

## Evidence gates

- A task proves its own selection, the integration branch proves the suite. Task (`ready`, every route): every selected test green in CI on its SHA, by one Picked tests run of the list `verify --picked-list` prints (a raw-map file carries `+`) or by several runs whose coverage adds up; plus `verify --check` (syntax and table freshness: Picked tests do not run them). A full PR checks run on the task SHA also counts (it covers the default suite, 12 distinct successful shards, and the check; raw-geodata-only tests still need Picked tests) but is not asked. Suite: full PR checks run on the integration branch head after every landing; the `land` tool starts them and refuses the next landing while the head's run is missing, still going or red, except the declared fix of a red head (`land --fixes-red`); the release gate ci asks them green on the frozen head. Why (maintainer 2026-11-13): in release 1b.0f both tests that a task's full run failed on were inside that task's selection (259 and 109 of 1280 tests).
- Picked tests: require exact SHA or single-parent list commit adding only ci-tests.txt, successful Plan and expected shards.
- Always run local mechanical rules-check for HEAD (verify --rules); PR checks includes syntax/table check but not planning/rules-check.js. --selection-ack records reviewer judgement for an uncertain selection (a deleted file, a non-JS change, no selected tests); a critical surface is a route check and asks no ack. No automatic dispatch.
- Review: `record-review --result pass|blocked --evidence <ref> --rules <file>` reads the review table from the file (other lines are ignored): one line per hard rule 0-15 and one for `cause` (is the cause fixed in the mechanism that owns the rule), each `<rule> ok <evidence>`, `<rule> na <reason>`, `<rule> violation <file:line> <what>` or `<rule> left <lc id[,id]> [M<n>] <reason>`. The first review of a brief answers all 17; a later round gives only the lines it changes and they replace the earlier answers. A pass with a violation standing is refused, a blocked review names at least one violation, and `ready` refuses an unanswered rule or a standing violation. `left` lets a named lc issue stand where the rule's own text allows it (2, 4, 15, cause); for any other rule it needs a maintainer decision id (`lc decide`), and `lc land` checks the issues and the decision exist. `--taken-out <ids>` names small fixes the review took out. Every round is kept in the record (`reviews`). A task that changes a generated table, its generator or its fingerprint (`data/Bots/`, `scripts/generate*`, `TableFingerprint`) gets its first review recorded only when HEAD already holds the CI evidence `ready` asks (the selected and raw-map tests green in CI): the real reader has then run over the whole built table before a reviewer reads the change, so send the reviewer after that CI.
- Fixes record the expected old assertion failure and new pass (base SHA and evidence reference) with record-regression; manual evidence, not an automated old-code execution. Every named regression test needs its own receipt; regression tests are a subset of brief tests. Preserve existing independent review, simulation and release A/B requirements.
- Same tree: evidence recorded on one commit (review, rules, regression receipts, CI runs) holds on another commit that has its tree, since the base and the content are the same change. So a task's commits may be folded into one at landing (the `land` tool does it and checks the folded message for AI lines), and the folded head's full run is recorded on the task from its worktree (`ci-finish <slug> <worktree> --sha <the landed head>`). A commit with another tree carries nothing.
- ready is task evidence, not merge authorization. `record-land --remote <r> --branch <b>` records that the remote branch holds the verified tree; no automatic push/merge. If batch integration changes the tree, do not transfer evidence: reverify the integrated result. Final full integration CI still mandatory.
- Retro: `ready`, `record-land` and `close` print `RETRO DUE: <reason>` (a critical violation, one cause twice, or 5 open candidates). The coordinator then sends one narrow Retro agent (common root cause, consequences, minimal guard, result saved) and marks them `record-retro <slug> --processed <ids|all> --result <path>`. No standing process, nothing fires by itself: a candidate counts only once the coordinator records it (`record-retro --cause --text`) when it reads the report or writes the handoff.
- Digest = workflow.js, evidence.md, routes.md (what defines evidence); CLAUDE.md, the other references, hygiene and lc change without voiding open records. The three digest files change only between releases (no release open in lc) or for a defect that blocks work, as one batch: every edit voids every open record. It does not pin map files; use exact file/line/trace handles and re-evaluate if they change.

## Limits
No automatic old-code restoration, trace query or invariant extractor yet: the old-code failure and the review are recorded references the coordinator inspects, not something the CLI ran. Single coordinator per slug; two commands on one slug may overlap: each writes only its own change onto the record as it is then, and one that replaces what the evidence stands on (record-brief, record-rebase, close, ready, record-land) refuses when the record changed under it.
