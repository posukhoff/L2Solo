# Task evidence

## Cause gate and handoff

Separate symptom from hypothesis in the issue (`lc add`; problems.md is its rendered line): cause: guess or verified + trace/test/source ref. Guesses enter investigation, not implementation; critical blockers get immediate triage. A cause is verified when its chain runs from the observed symptom to the first wrong decision or broken invariant (C4 rule, situation, owner contract). The chain names where the symptom shows apart from the mechanism that produced it, rules out each plausible alternative with a handle, and is proven by a reproduction, trace or counterexample that accounts for the counted symptom, not one instance. The first wrong decision is the earliest one in the chain that you can prove, not the one nearest the symptom. Follow the chain to the deepest cause you can prove and fix that one, in its owner (planning.md "Deeper causes"); stop at a nearer cause only when the deeper one is replaced by a planned release or needs its own critical task, and then name it: `deeper cause: left as <lc id> because <which of the two>`. Whoever writes the cause chain (the planner, or the coordinator when no planner runs) writes this line into the brief as `cause.deeper` (`fixed here` or `left as <lc id> because …`; `record-brief` refuses a verified cause without it, `lc land` checks the issue is open); the review's `cause` line checks it against the code. Before fixing the owning mechanism ask hard rule 0 of it: is it needed at all (deleting it is a fix). Unproven after one bounded investigation → blocker. Independent causes get separate linked slugs. Containment of a serious defect is labelled temporary, with an open root-cause lc issue. Briefs carry exact base and evidence handles; implementer spot-checks a decisive handle, reinvestigates only if contradicted. Coordinator resolves overlapping owner scopes before edits; review stays scoped.

Start with --kind fix (default), feature or chore. A guess is investigation-only. CLI validates shape, not truth; coordinator inspects evidence. New brief resets task evidence; changed policy requires new slug. Keep evidence handles, not secrets/log dumps. Sample:

```json
{
  "base": "<full task base SHA>",
  "symptom": "Observed incorrect town departure",
  "owner": "BotSpotTravel: departure/recovery",
  "cause": {"status":"verified","explanation":"What caused the observed failure","chain":["where the symptom shows (file:line)","first wrong decision or broken invariant (handle)"],"excluded":["plausible alternative ruled out (handle), or none plausible: reason"],"deeper":"fixed here","evidence":["run ID / trace record / source file:line"]},
  "scope":["src/..."],
  "nonGoals":["Unrelated field recovery"],
  "acceptance":[{"expect":"Expected observable behaviour","by":"test_bot_town_travel.js"}],
  "map":["world.md: Town departure"],
  "smallFixes":[{"id":"DT-375","file":"src/..."}],
  "evidence":["Saved run ID and SQL result reference"],
  "tests":["test_bot_town_travel.js"],
  "regressions":["test_bot_town_travel.js"]
}
```

Each acceptance line names what pins it in `by`: a test listed in `tests` (a case name may follow the file), or `run: <record>` / `trace: <record>` when only a run shows it. `map` names the architecture-map entries the task changes, each `<file>.md: <entry>`, or is one `none: <reason>`; the release report gate checks that each named file was refreshed after the landing. A feature or chore also names `guards`: what must not get worse while its target moves, each `{"expect": <the number and its bound>, "by": <a test or "run: <record>">}`, or one `none: <reason>` (2026-11-12: a task raised a total from 39 % to 55 % while one level band fell from 44 % to 9 %). `smallFixes` (optional, at most 4) names each small fix the task carries (planning.md "Small fixes") by lc id and the one source file it changes: `ready` requires one commit per id, the id in its subject, changing that file and tests only.

A record ends by landing or by `close <slug> --evidence <ref>` with `--refuted` (a guess that proved wrong) or `--abandoned` (any task not landed: where its work went or why it stopped); a closed record takes no more evidence, and one opened under an older digest can still be closed.

A guess brief needs only base, symptom, evidence and cause hypothesis; complete owner/scope/acceptance/map/tests before verification. Feature/chore omit cause/regressions but supply `symptom` (the goal, in that field), owner, scope, nonGoals, evidence (spec/reference), acceptance, map and tests; the goal states what is to be built or measured, never an unmeasured cause as a fact. No source edits are done by CLI.

## Evidence gates

- A task proves its own selection, the integration branch proves the suite. Task (`ready`, every route): every selected test green in CI on its SHA, by one Picked tests run of the list `verify --picked-list` prints (a raw-map file carries `+`) or by several runs whose coverage adds up; plus `verify --check` (syntax and table freshness: Picked tests do not run them). A full PR checks run on the task SHA also counts (it covers the default suite, 12 distinct successful shards, and the check; raw-geodata-only tests still need Picked tests) but is not asked. Suite: full PR checks run on the integration branch head after every landing; the `land` tool starts them and refuses the next landing while the head's run is missing, still going or red, except the declared fix of a red head (`land --fixes-red`); the release gate ci asks them green on the frozen head. Why (maintainer 2026-11-13): in release 1b.0f both tests that a task's full run failed on were inside that task's selection (259 and 109 of 1280 tests).
- Picked tests: require exact SHA or single-parent list commit adding only ci-tests.txt, successful Plan and expected shards.
- Always run `verify --check` for HEAD (syntax, table freshness as CI judges it, and the mechanical rules of planning/rules-check.js, which no CI runs); `verify --rules` runs the rules alone. --selection-ack records the reviewer's answer for an uncertain selection (a deleted file, a non-JS change, no selected tests): its report says per warning whether the selection covers the change, and without that answer the flag is not given; a critical surface is a route check and asks no ack. No automatic dispatch.
- Implementer report: `record-report <slug> --file <report>` reads four kinds of line from the implementer's report: `added beyond the plan: none | <each addition and what breaks without it>`, `deviations from the plan: none | <each>`, `tests run: <files; the assert each regression test fails at on the old code>`, and one `guard: <before -> after>` per guard of the brief. `ready` refuses a head without it; the reviewer answers rule 0 for each addition. `.claude/tools/brief <slug> <worktree> <role> --out <dir>` prints each agent's brief from the record (the report form for the implementer, the recorded report for the reviewer): the coordinator adds facts with `--notes` and retells no rule.
- Review: `record-review --result pass|blocked --evidence <ref> --rules <file>` reads the review table from the file (other lines are ignored): one line per hard rule 0-15 and one for `cause` (is the cause fixed in the mechanism that owns the rule), each `<rule> ok <evidence>`, `<rule> na <reason>`, `<rule> violation <file:line> <what>` (a commit message: `<rule> violation commit <sha> <what>`) or `<rule> left <lc id[,id]> [M<n>] <reason>`. The first review of a brief answers all 17; a later round gives only the lines it changes and they replace the earlier answers. A pass with a violation standing is refused, a blocked review names at least one violation, and `ready` refuses an unanswered rule or a standing violation. `left` lets a named lc issue stand where the rule's own text allows it (2, 4, cause); for any other rule, and for a step away from the target architecture (15), it needs a maintainer decision id (`lc decide`), and `lc land` checks the issues and the decision exist. `--taken-out <ids>` names small fixes the review took out. Every round is kept in the record (`reviews`). A task that changes a generated table, its generator or its fingerprint (`data/Bots/`, `scripts/generate*`, `TableFingerprint`) gets its first review recorded only when HEAD already holds the CI evidence `ready` asks (the selected and raw-map tests green in CI): the real reader has then run over the whole built table before a reviewer reads the change, so send the reviewer after that CI.
- Fixes record the expected old assertion failure and new pass (base SHA and evidence reference) with record-regression: the implementer restores the old code of the fix, runs each regression test and reports the failing assert with the base SHA, the reviewer re-runs one of them, and `--evidence` cites that report; manual evidence, not an automated old-code execution. Every named regression test needs its own receipt; regression tests are a subset of brief tests. Preserve existing independent review, simulation and release A/B requirements.
- Same tree: evidence recorded on one commit (review, rules, regression receipts, CI runs) holds on another commit that has its tree, since the base and the content are the same change. So a task's commits may be folded into one at landing (the `land` tool does it and checks the folded message for AI lines), and the folded head's full run is recorded on the task from its worktree (`ci-finish <slug> <worktree> --sha <the landed head>`). A commit with another tree carries nothing.
- ready is task evidence, not merge authorization. `record-land --remote <r> --branch <b>` records that the remote branch holds the verified tree; no automatic push/merge. A rebase onto a base that left the task's files unchanged keeps the review and the regression receipts through `record-rebase`; CI receipts hold only on the same tree; any other change of the tree is reverified. Final full integration CI still mandatory.
- Retro: `ready`, `record-land` and `close` print `RETRO DUE: <reason>` (a critical violation, one cause twice, or 5 open candidates). The coordinator then sends one narrow Retro agent (common root cause, consequences, minimal guard, result saved) and marks them `record-retro <slug> --processed <ids|all> --result <path>`. No standing process, nothing fires by itself: a candidate counts only once the coordinator records it (`record-retro --cause --text`) when it reads the report or writes the handoff.
- Digest = workflow.js, evidence.md, routes.md (what defines evidence); CLAUDE.md, the other references, hygiene and lc change without voiding open records. The three digest files change only between releases (no release open in lc) or for a defect that blocks work, as one batch: every edit voids every open record. A change to a reference outside the digest applies to open records from the next agent launch, and the coordinator names the changed file in that brief. A task that makes generated tables stale rebuilds them on the fork before its CI (`verify --check` refuses stale tables); `land` makes the builds one commit. It does not pin map files; use exact file/line/trace handles and re-evaluate if they change.

## Limits
No automatic old-code restoration, trace query or invariant extractor yet: the old-code failure and the review are recorded references the coordinator inspects, not something the CLI ran. Single coordinator per slug; two commands on one slug may overlap: each writes only its own change onto the record as it is then, and one that replaces what the evidence stands on (record-brief, record-rebase, close, ready, record-land) refuses when the record changed under it.
