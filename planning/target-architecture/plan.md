# Target architecture: a data core that scales (open large plans)
Goal: ~1700 bots today on modest hardware, 5-10k later (possibly after a Rust rewrite). Decision cadence (situations) is built: architecture/population.md "Situations". Open here: the shape principles, components, typed arrays, sharding, memory as source of truth with the DB writer. Scaling numbers: memory.md "Scaling"; problems C12, POP-23.
## Principles
- Strategic DDD for the system's shape: bounded contexts with one owner each (combat, economy, population, party and clan, world, persistence; the context map is planning/architecture/); situations are the domain events between contexts; a bot state is an aggregate replaced, not edited, by its owner; C4 terms in code, map and talk. Not tactical OO DDD (entity classes, repositories, service layers): it fights pure rules on plain data, worker messages, memory and a Rust port.
- An ECS-like data core for the cold simulation: entity = bot id; components = flat data per kind with one owner each (position, vitals, bag, kit, occupation, plan); systems = the per-step pure functions (rounds, travel, regen, effects). Decisions are not systems: they run on situations above the components. The hot path (NodeL2 classes, packets) stays.
- Bot memory (maintainer 2026-11-09): no `botMemory` aggregate; one owner per topic (spot knowledge: `SpotRiskPolicy`; people: `InteractionMemory`; items: gearMarks' owner), each a component; every entry's lifetime is a named situation (outing end, level, new gear, joined a party), never steps or ms; one forget-on-situation mechanism beside `Situations` that owners declare entries on (as decisions declare wakes). Release 1: spot knowledge on it (DT-100); the rest DT-101
- Competition (maintainer 2026-11-09): contested resources are allocated by competition, not by an omniscient filter: bots choose by fit and common knowledge (a spot's usual crowd, not its live count), and at the resource the stronger unit (level, gear, party, clan party) holds it and displaces weaker ones, who move on; relations and persona modulate (clanmates share, aggressive risk PvP). Spots in release 1; later raid bosses and other contested things
- Scale out, not only cheaper: one worker cannot carry 5k bots; data by id makes sharding possible.
## Order of the large work
1. Memory as the source of truth, the DB a write-behind store (maintainer 2026-11-08, release 4 first): DB ≈ 29 % of main CPU; board settlement ~4600 tx/h (each reads the bag twice); revision CAS in SQL caused release 1's stale-refusal races. Design: main owns state in memory (single-threaded, CAS on an in-memory revision); an append-only operation journal flushed every 100 ms-1 s + periodic consistent snapshots, recovery = snapshot + journal replay (Redis/PostgreSQL/L2J autosave practice); one operation (a trade: both sides) = one batch in one transaction; coalesce a row's changes per flush; player-facing operations flush at once; bounded write queue with a counted lag; ordered, idempotent apply; a kill -9 recovery test. Then the DB writer worker only applies batches (main never waits on it).
2. Components: split the cold bot state into owned components; commits and worker messages carry the touched components only (today ~2.4 ms per commit, whole ~20 KB rows).
3. Typed arrays for the simulation core's numbers by id (one slab per table, not many small typed arrays).
4. Sharding bots over several workers.
## DB writer worker
Main spends ~28 % of busy time in the world DB (7e2be3a44 cold: `Database.js` ~39 s CPU per 10 min; longest turns `Database.execute` 184 ms, `ColdCommitQueue.flushBatch` 121 ms). DB time split (7e2be3a44, main busy 14.1 s/min): DB jobs 4.9 s/min incl (35 %), 87 % serving the cold worker, only 18 % the commit batch; life-state chain (bot-life save 1252/min, progress/vitals, soul crystals, inventory sync, publish: 4-5 queued jobs per resolve) 33 %, economy commands (npc purchase, afk trade, skill learn, board, meetings) 36 %, reads 6 %, maintenance 0.5 %. Moving only the commit batch gains ≤ 1.25 s/min gross, ~0.9 net (proposal forwarding ~25 MB/min, rows back ~11 MB/min), and two writers make main sleep on SQLITE_BUSY (busy_timeout 5000). First slice: (1) the life-state chain as one named plain-data command in one transaction (pays on main before any thread move); (2) then the commit batch + that command to the writer (~2.5 s/min, ~18 % of main busy); (3) economy commands later; (4) settle the two-writer rule first. Blockers: coordinator main-state gate before commit (`ColdSimulationCoordinator` ~1580-1609), request built from main state (`ColdSimulationOwner` ~186-255), closures in transactions (`Database` ~6363-6626, `performTransaction` → `ClanReviewInputs`), module memory inside the commit (`pendingSettlementOwners`), JS hooks bound to main's connection (`EconomyJournal` ~181, `ClanReviewEvents` ~235), game data in SQL paths (`dropPkDeathItemsUnsafe`, `historyOutboxUnsafe`), post-commit effects (`afterCommit`, `fenceBot`), read-your-writes in the life-state chain. Also the home of the situation-bit SQL writer and forming commits.
## Aggregates and the shard key (maintainer question, open)
- Bot: the main aggregate (life row + body: level, kit, bag, wallet, held decisions); decisions on the worker, bits only through `Situations.raise`, the row only through commits; the ECS components are its parts. Spot: who stands, room, kill share; decides the arrival contest and `enemy_met`; owner the worker. Party: objective + its decisions. Clan: raises to members, parties and the board. Board: postings and per-item waits, partitioned by town (`store.town`); trade-chat adverts span towns; a town is the board's partition key, not an aggregate (a town aggregate only with sieges/castle tax). Region: no decisions; a spatial index.
- Shard key open: by bot id splits a spot's hunters across workers (contest and `enemy_met` cross-thread); by region keeps a spot and a town whole and hands a bot over when it travels (as the hot/cold handoff). Constraint now: spot, town and party data keyed by their own id, never stored inside bot records, so either key stays possible.
