# Research Note — Аудит One World Experiment v0.6–v0.7

- **Статус:** Исследовательские выводы и предложения; не ADR и не принятое архитектурное решение
- **Дата:** 2026-11-17
- **Контекст:** L2Solo, One World Experiment v0.6–v0.7
- **Связанные документы:** [ADR-001](../adr/001-domain-model.md) (Accepted), [ADR-002](../adr/002-decision-system.md) (Accepted), [ADR-003](../adr/003-gameplay-execution.md) (Accepted), [ADR-004](../adr/004-simulation-runtime.md) (Draft), [архитектурный backlog](../BACKLOG.md)
- **Область:** способ проверки архитектуры симуляции, критерии достоверности бенчмарков, граница между экспериментом и продуктовым кодом
- **Не определяет:** реализацию Hot/Cold, структуру воркеров, ECS, базу данных, алгоритм Decision System, формулы C1–C6 и SLO целевого ПК. Не заменяет и не изменяет ADR-001–004.

## 1. Контекст и проблема

L2Solo должен обеспечивать **один живой мир** с автономными Account/Character, одновременно и взаимосвязанно исполняя PvE, PvP, рейды, осады, перемещение, скиллы и массовое лечение, торговлю/крафт/ресурсы и принятие решений AI. Целевой масштаб обсуждается отдельно для **Account** (до 7 000 как испытательный профиль) и **Character** (до 10 000 как стресс-профиль); они не взаимозаменяемы. Конечное ограничение — обычный пользовательский ПК с проверкой на целевом оборудовании.

Java 21 One World Experiment создавался **как синтетический бенчмарк нагрузки и архитектурных идей, а не как реализация сервера**. При попытке сделать его реалистичнее возник риск повторно реализовывать игровые подсистемы, которые затем пришлось бы переписывать в целевом стеке. Числа из такого эксперимента не доказывают работоспособность полноценного сервера и не определяют автоматически выбор архитектуры.

## 2. Предлагаемое направление (не принято отдельным ADR)

1. **Предлагается остановить функциональное расширение Java One World Experiment после v0.7.** Не разрабатывать «v0.8» ради новой версии или ради приближения Java-прототипа к полноценному игровому серверу. Архив v0.7 и результаты сохранить как исследовательские данные и контрольные сценарии.
2. **Предлагается перейти к минимальному работающему Simulation Core в целевом стеке TypeScript/Node.js**, ориентированному прежде всего на честные headless-измерения. Это не решение писать все механики/весь сервер сразу. Использовать существующую доменную модель ADR-001, не менять её на основании синтетического бенчмарка.
3. **Предлагается сохранить узкие микробенчмарки** (в том числе Java, если они полезны) для сравнения *конкретных* алгоритмов с одинаковой нагрузкой, но не использовать их абсолютное время как прогноз производительности сервера на TypeScript.
4. **Предлагается проверить архитектурные гипотезы в настоящем ядре**: Hot/Cold и переходы между ними, длительная/неограниченная по времени обработка событий, стоимость решений Account, пространственный поиск, массовый бой, непрерывная экономика и сохранение инвариантов. Не считать Hot/Cold, ECS, Worker Threads, многопоточность, Rust или GPU уже выбранной реализацией — только кандидатами для измерения.
5. **Рекомендуется Benchmark Harness с первого этапа**: виртуальное время, фиксируемые seed/профили, headless-прогоны, независимые метрики CPU/RAM/latency и корректности; сравнение нескольких реализаций на одном и том же зафиксированном сценарии.
6. **Архивировать результаты как самостоятельные исследовательские материалы.** Сама заметка не меняет статус ADR-001–004. Перенос в Git выполняется только по явной команде владельца проекта.

## 3. Подтверждённые находки аудита v0.6–v0.7

### F-01. DETAIL/BATCH — два планировщика событий, а не Hot/Cold

В `CombatPrototype.java` `DETAIL` реализован через `PriorityQueue<Event>`, `BATCH` — через календарь корзин `ArrayDeque<Event>[]` с дискретностью 1 мс. Оба запускают одинаковые детализированные боевые правила и общий World. В `BucketScheduler` память под корзины выделяется заранее по времени теста; `World` ограничивает длительность **1–120 игровых секунд**. Это не доказательство непрерывной работы и не реализация Cold-агрегации.

**Следствие:** выбор Hot/Cold, стоимость handoff, точность результатов Cold и выигрыш по CPU пока **не измерены**.

### F-02. Измерения не поддерживают выбор «лучшего» планировщика

Повторённый прогон v0.7: `7 000 Account / 7 000 Character`, 8 игровых секунд, seed 42, Java 21, **три пары запусков в одном процессе** (порядок всегда DETAIL → BATCH):

| Пара | DETAIL, мс | BATCH, мс | Результаты |
| --- | ---: | ---: | --- |
| 1 | 2886.380 | 2322.253 | Совпадают |
| 2 | 2261.590 | 2128.266 | Совпадают |
| 3 | 2229.376 | 2198.081 | Совпадают |

Разрыв уменьшается при последовательных прогонах. Эти результаты **не подтверждают устойчивый выигрыш** BATCH: прогрев JIT, GC, порядок запуска, аллокации и шум системы не отделены. Это не p95/p99, не измерение на целевом ПК. Нельзя напрямую сравнивать времена v0.6 и v0.7: v0.7 включает инициализацию мира/ledger в `elapsed_ms`, в отличие от исторической методики v0.6.

**Требование к будущим замерам:** фиксировать JVM/Node версии, оборудование и режимы, прогревать, варьировать порядок, многократно повторять в независимых процессах, публиковать распределения/перцентили, отдельно измерять startup и steady-state, событий/сек и CPU-время.

### F-03. «7 000 Account» не означает «7 000 одновременно сражающихся Character»

Повторяемая v0.7-проверка, seed 42, 8 игровых секунд:

| Показатель | 7k Account / 7k Character | 7k Account / 10k Character |
| --- | ---: | ---: |
| NPC и боссы | 3 175 | 4 536 |
| Всего боевых сущностей (Character + NPC) | 10 175 | 14 536 |
| Character с активностью COMBAT, конец 8-й секунды | 4 208 | 4 452 |
| Character, совершившие атаку/скилл за 8-ю секунду | 2 945 | 2 924 |

В v0.6 была устранена фиктивная постоянная квота 5 600 бойцов. В v0.7 Account выбирает один управляемый Character (иногда альта), но **переключения Character во время работы нет**. Остальные Character остаются в мире и могут получать урон; они не становятся автоматически дополнительными AI-агентами.

**Следствие:** разделять в отчётах число Account, число присутствующих Character, число активных контроллеров, намерение COMBAT, реально выполнивших действия за интервал и число NPC. Тест 10k меняет также раскладку зон и NPC — это **не чистый тест добавления 3 000 Character**.

### F-04. Сценарии одного мира предустановлены, а не возникают из полноценных решений

`createMixed`/`zone` задают нагрузочный профиль примерно **45% PvE / 20% skirmish / 15% raid / 20% siege** по Character ID. Региональные рейдовые и осадные стимулы включаются по заданному времени. Account Goal — ограниченная синтетическая функция score из шести Goal и четырёх Activity, а не согласованный Decision System с долгосрочной памятью, знаниями, приказами CP/Clan и независимой мотивацией.

**Подтверждено:** общие игровые часы, единое боевое состояние и обработка действий PvE/PvP/raid/siege, NPC, движения и экономики в одном эксперименте. **Не подтверждено:** органическое возникновение и пересечение конфликтов, целостная модель интересов Account и достоверный поток событий полноценного сервера.

### F-05. Инварианты бухгалтерии есть, но экономические ограничения нагрузки неполные

В v0.7 раздельные кошельки Character, Account Warehouse, торговый escrow и проверки сохранения ore/shots/adena действительно реализованы. Однако `onPlayerAction` списывает shots только если они есть, не предотвращая и не меняя боевое действие при нулевом остатке. В проверке исходного архива v0.7 (7k/7k, seed 42) к **60-й игровой секунде у 1 173 из 3 504** Account с активностью COMBAT было ноль shots. При этом события боя продолжаются. Перечень заявок и складских остатков также сильно зависит от искусственно выданных стартовых ресурсов.

**Следствие:** «сохранение количества ресурсов» ≠ «экономика реалистично ограничивает поведение и CPU». Нужны сценарии дефицита, добычи, доступности рынка, логистики и замкнутых торговых цепочек; без этого нельзя делать вывод о нагрузке живой экономики. Исправление числа: предыдущая устная оценка **1 700 из 3 958** не подтверждается этим воспроизводимым прогоном.

### F-06. Метрики времени подсистем пересекаются

В `PopulationWorldExperiment.State.step()` `economyNs` измеряет блок с `dueDecisions()` и обработкой экономики, в то время как `decisionNs` отдельно суммируется внутри `reconsider()`. Поэтому `decision_ms` **частично входит в** `economy_ms`, эти числа нельзя складывать как независимые CPU-затраты. `elapsed_ms` в `run()` снимается **перед** `finish()`, который вычисляет итоговые digest — значит финальное хеширование состояния не включено в заявленное время. Кроме того, часть решений инициализации входит в `elapsed_ms`, но не в блок `economy_ms`.

**Следствие:** определить независимые интервалы (startup, world-tick, decisions, economics, index, serialization, persist, validation, teardown) и измерять их без двойного счёта; явно указать, какие расходы входят в целевое end-to-end время.

### F-07. Проверки корректности полезны, но ограничены моделью

Подтверждены: паритет `DETAIL/BATCH` на имеющихся наборах seed/сценариев; отсутствие отрицательных ресурсных балансов и дублирования товаров в ledger/escrow; раздельность Character-инвентарей; тестируемые ограничения Account Warehouse; существование пассивных Character в World и приём ими урона. Это **тесты на эквивалентность реализации упрощённых правил**, а не подтверждение соответствия L2 C1–C6, конкурентной многопоточности, persistence/restart или корректности Cold↔Hot.

### F-08. Память и время — свойства локального синтетического прогона

В архиве v0.7 один 30-секундный парный тест 7k/7k дал ~10.40 с DETAIL и ~9.16 с BATCH; `time -v` для процесса сообщил RSS **246 308 КиБ (~241 МиБ)**. Это RSS JVM-процесса за конкретный синтетический запуск, **не** оценка RAM готового сервера. Точные ограничения пользовательского ПК, целевые задержки и ресурсы ещё подлежат измерению и согласованию.

## 4. Варианты для архитектурного обсуждения

| Вариант | Предварительная оценка | Причина |
| --- | --- | --- |
| Продолжать усложнять Java v0.8/v0.9 | Отклонить как основную линию | Риск построить второй сервер; переноса абсолютных timings на TypeScript нет |
| Сразу писать полноценный сервер (клиент, C1–C6, весь контент) | Отложить | Слишком много переменных, невозможно быстро проверить архитектурную гипотезу |
| Минимальный настоящий Simulation Core + отдельные микробенчмарки | **Рекомендуется рассмотреть** | Проверяем производительность того кода и модели исполнения, которые дальше развиваем |

## 5. Предлагаемые границы первого Simulation Core

**Включить:** единое авторитетное World State; Account/Character разделение по ADR-001; виртуальное игровое время и событийное исполнение; минимальное реактивное поведение и измеримый cost Decision System; два уровня детализации Hot/Cold как *проверяемую гипотезу* с полноценной процедурой handoff; минимальные движение, бой, скиллы (single/AoE/heal), NPC, ресурсные транзакции и торговые заявки; детерминированные headless-профили нагрузки и измерения.

**Не включать на первом этапе:** игровой клиент/UI, полный пакет Chronicle C1–C6, все классы/скиллы/квесты, визуализацию, LLM в горячем пути, обобщённые сервисы без измеримой необходимости. Persistent state/restart и реальный клиент понадобятся отдельными этапами, но не должны блокировать первое доказательство производительности ядра.

**Не принимать преждевременных архитектурных решений:** ECS/набор Workers/Rust/GPU/широкое распараллеливание выбираются только после сравнимых профилей и выявленного bottleneck. В частности, «Hot = видимые реальному игроку Character с запасом» — ориентир из backlog, а не доказанная оптимальная форма реализации.

## 6. План проверки: что измерять следующим

| Приоритет | Эксперимент / вопрос | Критерий приемки доказательства |
| --- | --- | --- |
| P0 | **Точная метрика и непрерывный baseline** | Прогон без ограничения 120 с, повторяемость seed, фиксированные условия, CPU/RAM и latency-профили без перекрытия счётчиков |
| P0 | **Hot/Cold equivalence + handoff** | Сохранены инвентарь, HP, cooldowns, позиции, права, активные задания и результаты; ошибки контролируются при многократных переходах |
| P0 | **Единый мир при mixed workload** | PvE/PvP/siege/raid + экономика + решения исполняются вместе, нагрузка каждого вида измерима отдельно и совместно |
| P0 | **Инварианты экономики и дефицит** | Без дюпов, без неограниченных ресурсов/удалённых бесплатных действий; дефицит меняет поведение и нагрузку корректно |
| P1 | **Цены Decision System** | Измерено число пробуждений, обновлений целей, отмен и реакций на события при разных размерах популяции |
| P1 | **Массовые сражения + spatial search** | Сценарии плотного боя, AoE, массового хила, выбора целей/погони с фиксированным составом и явным учётом NPC |
| P1 | **Масштабирование 7k Account / 10k Character** | Отдельные controlled Character, присутствующие Character, NPC и реальная активность; нагрузки сравниваются с неизменным профилем |
| P2 | **Worker/ECS/Rust и иные оптимизации** | Только A/B-измерения с теми же исходными данными, инвариантами и целевой машиной |

Для каждого эксперимента: цель и гипотеза → неизменная fixture → ожидаемая корректность → несколько прогонов → распределения времени/памяти → вывод, включая отрицательный. **Сначала согласовать измеримый целевой CPU/RAM/latency budget на пользовательском ПК, затем утверждать «подходит / не подходит».**

## 7. Последствия для дальнейших исследований

- Java v0.7 остаётся **референсным синтетическим экспериментом** и набором проверок, а не кодовой основой сервера.
- Дальнейшие дорогостоящие механики создаются только если помогают проверить поставленную гипотезу либо нужны минимальному ядру.
- Реальная архитектура может оказаться частично другой; результаты v0.7 не обязывают использовать календарь 1 мс, глобальный фиксированный tick, тот же формат хранения или ту же эвристику Account.
- Любая архитектурная гипотеза (Hot/Cold, spatial index, event scheduler, concurrency) получает отдельное решение только после доказательств.
- ADR-001–003 сохраняют ранее согласованные области ответственности; ADR-004 (Runtime и масштабирование, Draft) является естественным местом для рассмотрения этих результатов. Эта заметка не меняет существующие решения.

Команды из каталога распакованного v0.7 (JDK 21):

```bash
javac -encoding UTF-8 CombatPrototype.java WorldEconomyExperiment.java CharacterEconomyV07.java PopulationWorldExperiment.java PopulationTrace.java SkillRulesTest.java
java SkillRulesTest
java PopulationWorldExperiment --test
java -Xmx2g PopulationWorldExperiment --accounts 7000 --characters 7000 --seconds 8 --seed 42 --repeats 3
java -Xmx2g PopulationWorldExperiment --accounts 7000 --characters 10000 --seconds 8 --seed 42 --repeats 3
```

Примечание: run использует фиксированный порядок DETAIL затем BATCH, поэтому `--repeats 3` сам по себе **не** исправляет систематическую погрешность порядка или JIT. Проверка t=60 проводилась отдельным локальным инструментом аудита `Probe.java` для чтения состояния `State` после шагов, не входящим в поставку v0.7.
