# L2 Solo — Testing Strategy

- **Статус:** Engineering standard (согласовано 2026-11-16)
- **Область:** все подсистемы следующей версии L2 Solo
- **Принцип:** **Tests protect behavior, not implementation.**

## 1. Назначение

Тесты защищают публично наблюдаемое поведение, доменные инварианты, контракты на границах подсистем и подтверждённые регрессии. Они не должны препятствовать корректному рефакторингу, расти автоматически вместе с числом классов или превращаться в описание внутренней структуры кода.

Тест, для которого нельзя назвать защищаемый риск, инвариант, контракт или дефект, не добавляется.

## 2. Что проверяем

| Уровень | Проверяем | Пример |
|---|---|---|
| **Unit (domain)** | Чистые правила и результаты через публичный контракт | При вступлении Account в CP эффективный Clan определяется CP, а прямая связь очищается |
| **Integration** | Взаимодействие настоящих компонентов на границе | Атомарное перемещение из Account Warehouse без двойного расходования |
| **Scenario / acceptance** | Конкретный бизнес- или игровой сценарий от команды до результата | CP вступает в Clan целиком или получает отказ при превышении социального лимита |
| **Property-based** | Универсальные инварианты для множества состояний | Суммарное количество ресурсов сохраняется при допустимых перемещениях |
| **Performance / benchmark** | Время, память, нагрузка и масштабирование | 10K Cold-персонажей, hotspot с реальными игроками, массовое PvP |

Бенчмарки хранятся и запускаются отдельно от быстрых unit-тестов; результат архитектурного ADR не считается доказательством производительности.

## 3. Правила написания

1. Тестировать **эффект через стабильный контракт**, а не приватные поля, число вызовов, порядок внутренних функций, расположение файлов или конкретные структуры классов.
2. Для поведения, не зависящего от времени и случайности, использовать воспроизводимые входные данные. Для симуляции — управляемые виртуальные часы и seed. Не использовать реальные задержки ради «ожидания» симуляции.
3. Моки и заглушки допустимы на **внешних границах** (сеть, LLM, системное время, persistence, внешние сервисы). Не мокать внутренние доменные объекты только чтобы подтвердить взаимодействие с ними.
4. Проверять успешный результат и существенные **запрещённые состояния**: превышение вместимости, двойной расход, конфликт контроллеров, потерю состояния при передаче владения.
5. Подходящий фикс подтверждённого бага сопровождается минимальным регрессионным тестом поведения, если он реально предотвращает повторение дефекта.
6. Сложность теста должна соответствовать риску. Не создавать по тесту на каждый класс, метод, условную ветку или событие.
7. Не вводить обязательный процент code coverage: покрытие — диагностика, не целевой KPI. При желании использовать mutation testing точечно для критичных инвариантов, без глобальной квоты.
8. При изменении поведения **пересматривать существующие тесты**: удалять устаревшие, дублирующие и недостаточно ценные вместо постоянного наращивания набора.

## 4. Контроль роста набора

Перед новым тестом автор отвечает на четыре вопроса:

- Какое наблюдаемое поведение, инвариант, контракт или регрессию он защищает?
- Есть ли уже тест, защищающий то же самое на подходящем уровне?
- Выживет ли тест при корректном рефакторинге реализации?
- Оправданы ли стоимость запуска и сопровождения значимостью риска?

Не дублировать дорогой end-to-end сценарий там, где достаточен короткий unit-тест, но и не заменять интеграционную проверку десятками замоканных unit-тестов. Выбирать **самый дешёвый уровень, который способен поймать нужный дефект**.

## 5. Приоритетные зоны риска L2 Solo

- **Экономика:** единственный владелец ресурсов; отсутствие генерации/утраты предметов при переводах; конкурентные операции.
- **Организации:** Account/CP/Clan принадлежность, формальные игровые права, атомарность изменений.
- **Управление:** полномочия, приказы, ручное вмешательство, отсутствие двух конфликтующих источников команд.
- **Симуляция:** один авторитетный владелец состояния, непрерывность задач и прогресса Hot ↔ Cold, одинаковые значимые последствия при сопоставимых сценариях.
- **Воспроизводимость:** виртуальное время, seed, restart/recovery; повторяемые результаты без зависимости от расписания ОС.

Конкретные примеры здесь иллюстрируют стратегию тестирования, **а не расширяют scope ADR-001**.

## 6. Definition of Done для поведения

Изменение считается защищённым тестами, когда:
- сформулирован внешний результат и ключевые риски;
- написаны или скорректированы минимальные проверки на подходящих уровнях;
- сохранены существующие инварианты;
- не добавлено тестов, которые зависят от необязательных деталей реализации.

Решения о фреймворке, структуре тестовых каталогов и CI принимаются при проектировании реализации, а не задним числом как требования к доменной модели.
